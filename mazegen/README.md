# Mazegen

This is my maze generator, written in Python as an extension to my maze game. My oral presentation is available at: https://www.youtube.com/watch?v=T158J5Jon5w

## Folder Structure

The project is organised such that the main files are in the root directory and previous iterations of my maze generation algorithm are in the `versions` directory so a progression can be observed.

In addition, the root contains some sample mazes of various dimensions generated by my algorithm and versions folder contains sample mazes generated by the respective iteration of the maze algorithm as per the title.

My final solution is a combination of the code in mazegen.py as well as maze.py. Maze.py defines the class that is used to actually generate my maze whereas mazegen.py primarily validates command line arguments and calls the maze generation function. 

Additionally, I have included a benchmarking script that can be modified to compare the time taken to generate mazes of different dimensions, sample output from that is included in benchmark.txt.

Mazes produced can be verified as valid by loading them into my maze game in the `maze_game` directory.

There are additional files in the versions directory that were used to test different iterations of my maze generation algorithm. The path_comparison.py script was used to compare the number of moves between start and end as generated by different versions of my algorithm and the time_comparison.py script was used to compare the time taken to generate mazes by different iterations of my solution.

## Usage
To generate a maze, run the following command:
```
python3 mazegen.py <mazefile path> <rows> <columns>
```
Where `<mazefile path>` is the path to the file you want to save the maze to and `<rows>` and `<columns>` are the dimensions of the maze you want to generate. Upon success, the program should output:
```
Maze written to <mazefile path>
```
To run the benchmarking script, use the following command:
```
python3 benchmark.py
```
The output should be like the below:
```
Average time to generate 5x5: 0.054 ms
Average time to generate 10x10: 0.208 ms
Average time to generate 20x20: 0.828 ms
Average time to generate 50x50: 5.141 ms
Average time to generate 80x80: 13.513 ms
Average time to generate 100x100: 21.173 ms
```

## Development

### maze_gen_v1.py

This is the first iteration of my maze generation algorithm. I created it without having read up on maze generation so the mazes it produces are relatively simple. It works by first creating random start and end points that would be at least `(rows + cols) / 2` steps apart. It then proceeds with a 'semi-random' walk whereby a path is carved from start to end by moving randomly either horizontally or vertically in the direction of end until it is reached. For anything outside of this path, a wall or empty space is randomly placed with equal probability.

This algorithm produced generally easy mazes since the main path was often obvious due to the randomness surrounding it and cycles would typically form since walls and spaces were randomly placed. Additionally, solutions were less winding than I would have liked, and the optimal or only solution had a fixed (albeit semi-random) path length.

To improve upon this, I decided that I should try implementing a more random walk to produce a windier path - that is moving in all random directions as opposed to just the 2 that would put me closest to the end.

### maze_gen_v2.py

I still hadn't researched maze generation algorithms at this point but decided to move ahead with improving on v1. This time I decided to set start and end a distance of `rand(10, max(rows, cols))` apart and calculate the end position as wherever I ended up after this number of moves. The new random walk moves preferentially towards the opposite diagonal but can still move outside of this path in a ratio of 3:1. Everything outside of the main path would still be a random wall or empty space.

This algorithm produced even worse mazes than v1. I found that paths tended to "clump" together as the walk ended up converging on the same location more often (the reason I avoided a proper random walk in the first case). Since the path often had so many areas of spaces, there would be a lot of solutions which made the maze less challenging. Since the results were so poor, I didn't bother working on this iteration any further, as such it still has obvious bugs that haven't been fixed. The one thing I did like about these 2 implementations was that the mazes generated looked fairly random and not like a grid which is the benefit of the maze ruleset provided.

To improve upon this, I decided to research maze generation algorithms and implement one that would produce more challenging mazes.

### maze_gen_v3.py

After researching maze generation algorithms, I decided to implement a recursive backtracking algorithm based on pseudocode from the [University of Washington](https://courses.cs.washington.edu/courses/cse326/07su/prj2/kruskal.html). My algorithm works as follows:
1. Produces an alternating grid of spaces bounded by walls as our maze
2. Randomly generates a starting point and generates an end point a distance apart as described in v1
3. Starting from the start point, the algorithm randomly picks a neighbouring cell and, if it has not been visited, moves to it breaking the wall in the process, and sets it as the current cell. If all neighbouring cells have been visited, the algorithm backtracks to the last cell with unvisited neighbours.
4. The algorithm recursively calls itself until there are no more unvisited cells.

This algorithm is quite effective in that it produces a perfect maze, that is a maze with no cycles and only one path between any 2 spaces, so the mazes produced are both always solvable and much more complex than my prior attempts. 

The issues here were that I implemented a recursive version of the algorithm, so it was slow and reached Python's recursion limit above a 45x45 maze. The start and end points were relatively predetermined and not necessarily best selected, there were often very long corridors with this implementation and mazes looked more similar to one another compared to my earlier attempts (that is, they looked like grids with fixed walls as opposed to more random as I intended).

To improve upon this solution, I decided to implement the non-recursive version of the algorithm and add random spaces after maze generation to make the mazes look more unique.

### maze_gen_v4.py and maze_gen_v4_modified.py

Using the pseudocode from [Wikipedia](https://en.wikipedia.org/wiki/Maze_generation_algorithm), I modified my solution to use the iterative implementation of the recursive backtracking algorithm. I also added a step after maze generation to randomly add spaces to the edge of the maze to make them look less like walls with a ratio of 2:1 in favour of keeping walls so that I didn't accidentally implement too many additional paths that made the maze trivial. The iterative implementation of recursive backtracking works as follows:
1. Produces a stack to keep track of visited cells starting with the start cell
2. Pops the current cell and check its neighbours
3. If a neighbour has not been visited, move to it, break the wall between the current cell and the neighbour and push the neighbouring cell to the stack
4. Repeat this until our stack is empty

This algorithm is much faster than the recursive version and can generate mazes of up to 100x100 in a reasonable amount of time.

The previous issues with my implementation did still stand though (i.e. start and end suboptimal, long corridors etc.) and while the solution did look more random than v3, it still looked less random than either v1 or v2. To attempt to alleviate this, I produced a modified version of this solution that introduced random spaces throughout the maze in cells that contained walls in a ratio of 3:1 favouring walls. Unfortunately, this produced mazes that were noticeably easier as it tended to create cycles and multiple paths between spaces. I also could not just add extra walls to compensate as that would have potential to make the maze unsolvable. 

Thus, I decided to revert to the original v4 implementation but decided to implement a more bounded version of depth-first search to reduce the long corridors and make the maze more branching inspired by this [StackExchange post](https://puzzling.stackexchange.com/questions/38/how-can-i-generate-mazes-that-often-have-multiple-forks-or-choices).

### maze_gen_v5.py

Here, I decided to modify my depth-first search recursive backtracker to occasionally pop a random cell from the stack as opposed to continuing along the current path. This would allow the algorithm to branch out more and create more winding paths. I tested some values for the probability of popping a random cell and found that setting it to `2 * (rows + cols) / 1000` seemed to work well as for lower probabilities, the maze would still have long corridors and for higher values, the maze would have too many obvious dead ends and be too easy. I use the maze dimensions in this calculation because many dead ends in smaller mazes makes them far easier to solve than dead ends in larger ones which are harder to immediately see.

This had the effect of making resultant mazes look more random and complex, but corridors could still be fairly long. At this point, I figured that the structure present in these mazes were a somewhat necessary tradeoff between complexity of the solution and the more generic visual appearance as mazes with wide areas of walls and spaces tend to be easier to solve at a glance.

To improve, I now wanted to calculate the maze starting point first so that the mazes could have walls on either even or odd indexed edges as opposed to what I had been doing before where initially the maze had walls always bounding the spaces at the edges of the matrix and I also wanted a more consistently difficult path by determining the end point based on the longest path from start in the maze.

### maze_gen_v6.py

Now I decided to improve my depth-first search implementation by tracking the furthest node from the starting point based on this [Altacademy blog post](https://www.altcademy.com/blog/compute-the-diameter-of-a-tree-solved/#:~:text=The%20diameter%20of%20a%20tree%20can%20be%20computed%20using%20depth,the%20diameter%20of%20the%20tree). This works by keeping an equivalently sized array to the maze to store the distance from the start to each cell, constantly checking the distance from the start and updating the end to the cell with the greatest distance. I also calculated the starting cell first to produce more maze variety as specified above.

This implementation produced mazes that were more challenging and had a more consistent difficulty level than any prior attempt. The mazes were also more visually interesting as they had more variety in the placement of the walls and spaces. There was still a way to produce a more difficult maze based on this solution though which would be making the start and end points the end nodes of the maze diameter which would require additional computation.

### maze_gen_v7.py

I learned that as a depth-first search maze is perfect, you can consider it an undirected tree and use 2 path finding algorithms to deduce the tree diameter, and the nodes at the ends of this longest path. Specifically, a breadth-first or depth-first search from a random node will give you the furthest node from that node and then a repeat of this starting from that node will produce the longest path in the tree ([StackOverflow Proof](https://stackoverflow.com/questions/20010472/proof-of-correctness-algorithm-for-diameter-of-a-tree-in-graph-theory)). I implemented this in my solution to calculate the start and end points of the maze. Since I had already done the first part in my depth-first maze generation, I added a breadth-first search based on this [GeeksforGeeks implementation](https://www.geeksforgeeks.org/longest-path-undirected-tree/) as follows:
1. Resets the start point to the furthest cell from the start point as per the depth-first search
2. Creates a queue and adds the start point to it
3. Regenerates the distance array and create another 2D array to track visited cells
4. Pops the current cell and check its NESW neighbours are unvisited
5. If they are, adds them to the queue and updates the distance array and visited array
6. If the distance to this cell is greater than the current max distance, updates the max distance and the end point
7. Repeats until the queue is empty

This procedure will always produce the longest mazes possible from this algorithm which would generally be the most challenging to solve. It should be noted, that since extra spaces are added after this point, this may no longer be the longest path, but that seems to be a worthy trade-off as far as making the maze appear more random. We could theoretically calculate the longest path after adding the spaces, but this would take more effort as the spaces can induce cycles and would likely not produce a significantly more challenging maze since spaces are only added at the edges anyway.

This process seems to produce a consistently challenging maze that is visually interesting and has a variety of structures, thus it is the version I adapted for my final submission.

### Testing

Upon implementing the final version of my maze generation algorithm, I decided to test it against the previous versions to see how it compared in terms of time taken to produce mazefiles. I used time_comparison.py to do this and the results are as follows:

```
Version 1: Time to generate 10 100x100 mazes = 0.13587737083435059 seconds
Version 2: Time to generate 10 100x100 mazes = 0.13275527954101562 seconds
Version 3: Does not work above 45x45
Version 4: Time to generate 10 100x100 mazes = 0.30345702171325684 seconds
Version 5: Time to generate 10 100x100 mazes = 0.29967665672302246 seconds
Version 6: Time to generate 10 100x100 mazes = 0.30263590812683105 seconds
Version 7: Time to generate 10 100x100 mazes = 0.3330225944519043 seconds
```
As we can see, the simpler algorithms take roughly half the time to produce a mazefile relative to the more complex depth-first search implementations which are relatively consistent in terms of time taken. That seems like a worthy compromise considering how much more sophisticated the generated mazes are. 

Version 7 of the maze generator would consistently take 10% more time than version 6 to produce a maze of the same dimensions, so I began to wonder whether the difference in path length was worth the additional time taken to generate the maze. To test this, I used path_comparison.py to compare the path lengths of mazes generated by versions 6 and 7. The results are as follows:
```
Path Lengths of Longest Path in 100x100 Mazes using just DFS vs DFS and BFS
Run 1: 311 difference (200.6%)
Run 2: 329 difference (212.3%)
Run 3: 374 difference (233.8%)
Run 4: 214 difference (237.8%)
Run 5: 334 difference (245.6%)
Run 6: 287 difference (219.1%)
Run 7: 433 difference (244.6%)
Run 8: 236 difference (274.4%)
Run 9: 328 difference (210.3%)
Run 10: 267 difference (269.7%)
Avg difference: 311.3 (234.8%)
```
As we can see, using both depth-first and breadth-first search to produce the mazefile takes only 10% longer but produces an increased path length of over 200% for 100x100 mazes, that is to say it tends to triple the number of moves between the start and end so it is well worth the additional time taken to generate the maze as it would be significantly more challenging.

## Limitations and Improvements

- The maze produced still has relatively long corridors, this could be improved by adding more randomness to the maze generation algorithm at the expense of making the maze easier to solve. I could have tried implementing a different maze generation algorithm like Prim's or Kruskal's which tend to produce more branching, but recursive backtracking seemed conceptually simpler, produced good results and frankly, I didn't have the time.

- A more universal problem with perfect mazes is that they will always look quite structured (for example there cannot be a space surrounded by hashes) which is a shame since we have a lot of scope to produce random patterns based on the valid maze rules relative to typical mazes which tend to have fixed wall and space lengths. I did actually attempt to produce something more random using a cellular automata-based solution, but I couldn't get it to work very well, it tended to produce clumps of walls and spaces which made the maze trivial to solve but it would be interesting to implement in the future with better generation rules.

- There is a trade-off between maze complexity and maze appearance, the more complex the maze, the more visually structured it tends to look which is hard to circumvent at least with recursive backtracking.

- My solution produces close to perfect mazes (not actually perfect since the edges have been altered) where the start and end are based on the maze diameter which will definitely present a challenge as per the coursework brief, but perhaps too much so with higher dimensions as the mazes become quite large and the path becomes quite long.

- Perfect mazes are also not necessarily more challenging than those with large cycles since it would not be immediately obvious that you are walking in a loop as opposed to a approaching a dead end. It would be interesting to implement a solution that produces mazes with large cycles to see how they compare but less literature is available on this, and it would break down for smaller maze sizes. Perhaps optimally, we would have different regimes for different sizes of maze but frankly, I think the mazes I generate are difficult enough to solve.

- Throughout the process, I never actually questioned Python's basic random module, it seems good enough for this purpose, but truly random number generation requires more effort (i.e. background radiation, lava lamps etc.).

- My process of generating mazes is fast enough but is using a slow, interpreted language in Python and wildly inefficient code. It could be faster if implemented more efficiently in C but that would take a lot more time and effort which isn't conducive to the largely exploratory learning exercise.
